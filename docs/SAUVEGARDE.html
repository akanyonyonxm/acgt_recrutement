Sauvegarde de la plateforme ACGT

Base de données PostgreSQL + documents (pièces jointes) — procédure et bonnes pratiques.

Règle d'or. La sauvegarde est une opération en lecture seule : elle ne modifie ni ne supprime jamais les données. Elle se lance manuellement sur le serveur ou via cron — jamais dans le pipeline de déploiement (qui, lui, ne touche pas non plus à la base).

1. Où vivent les données sur le serveur

En production (VPS Linux), tout est dans des volumes Docker persistants qui survivent aux redéploiements. Ils ne sont pas dans le dossier du projet.

ÉlémentVolume DockerEmplacement sur le serveur
Base de données PostgreSQL acgt_pgdata /var/lib/docker/volumes/acgt_pgdata/_data
Documents (pièces jointes des dossiers et réclamations) acgt_media_data /var/lib/docker/volumes/acgt_media_data/_data
Dans le conteneur applicatif, les documents sont montés sur /app/fichiers_prives (MEDIA_ROOT). Ils restent privés : jamais servis directement par Nginx, seulement via un téléchargement authentifié. Ne jamais éditer ces fichiers à la main.

2. Où seront stockées les sauvegardes bonne pratique

Les sauvegardes sont écrites dans un dossier dédié, hors du projet et hors des volumes Docker : 

/srv/acgt_backups/
├── db_2026-06-10_020000.sql.gz      ← dump compressé de la base
└── media_2026-06-10_020000.tgz      ← archive des documents
  • Fichiers horodatés et compressés.
  • Rotation automatique : les sauvegardes de plus de 30 jours sont supprimées (réglable).
  • recommandé Copier régulièrement ce dossier hors du serveur (autre machine, stockage objet, disque externe) — une sauvegarde sur la même machine ne protège pas d'une panne disque.

3. Lancer la sauvegarde

Sur le serveur, à la racine du projet :

chmod +x scripts/sauvegarde.sh
./scripts/sauvegarde.sh

Le script effectue, dans l'ordre :

  1. Base → pg_dump compressé : db_<date>.sql.gz
  2. Documents → archive du volume : media_<date>.tgz
  3. Rotation → suppression des sauvegardes trop anciennes

Options (facultatives) :

# Changer le dossier de destination et la rétention
BACKUP_DIR=/mnt/backups RETENTION_JOURS=60 ./scripts/sauvegarde.sh

4. Automatiser (cron) recommandé

Pour une sauvegarde quotidienne à 02h00, éditer la crontab du serveur :

crontab -e

puis ajouter (adapter le chemin du projet) :

0 2 * * * cd /srv/acgt_recrutement && ./scripts/sauvegarde.sh >> /var/log/acgt_sauvegarde.log 2>&1
Vérifier ensuite régulièrement le journal /var/log/acgt_sauvegarde.log et la présence des fichiers récents dans /srv/acgt_backups/.

5. Restaurer une sauvegarde

La restauration écrase les données actuelles. À faire en connaissance de cause, idéalement après avoir arrêté l'application.

5.1 Base de données

# Décompresser puis réinjecter dans la base
gunzip -c /srv/acgt_backups/db_2026-06-10_020000.sql.gz | \
  docker compose -f docker-compose.db.yml exec -T db psql -U acgt acgt_recrutement

5.2 Documents

# Restaure les fichiers dans le volume des documents
docker run --rm -v acgt_media_data:/data -v /srv/acgt_backups:/backup alpine \
  sh -c "tar xzf /backup/media_2026-06-10_020000.tgz -C /data"

6. Vérifier une sauvegarde

# La base : doit contenir du SQL lisible
gunzip -c /srv/acgt_backups/db_*.sql.gz | head -n 20

# Les documents : lister le contenu de l'archive
tar tzf /srv/acgt_backups/media_*.tgz | head
En résumé. ./scripts/sauvegarde.sh sauvegarde à la fois la base (acgt_pgdata) et les documents (acgt_media_data) dans /srv/acgt_backups/, avec rotation. Planifiez-le en cron et copiez les sauvegardes hors du serveur.
